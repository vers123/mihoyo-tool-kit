# 米游社工具箱 — RPA 适用性评估

> 评估对象：`miHoYo_ToolKit`（基于 Playwright + PySide6 的米游社/微博数据抓取工具）
> 评估日期：2026-09-02
> 评估分支：`docs/rpa-evaluation`
> 评估结论先行：**不建议整体迁移到 RPA**；仅在个别"需要人工辅助登录态"或"桌面+Web 混合"的边缘场景可考虑 RPA 补充。

---

## 一、项目现状速览

| 维度 | 现状 |
| --- | --- |
| 技术栈 | Python 3.8+ · Playwright ≥1.40 · PySide6 ≥6.5 |
| 抓取方式 | **API 拦截抓取**（`page.on('response')` 拦截 `content_v2_user` REST API），非 UI 模拟点击 |
| 数据规模 | 原神 4637 条 / 绝区零 1554 条 / 星穹铁道 792 条 |
| 登录态 | 读 Firefox `cookies.sqlite` 自动注入，无需手动登录 |
| 容错 | HAR 文件回退 + 自动备份 + 增量更新 |
| 入口 | CLI（32 项菜单）+ GUI（PySide6，左导航+底部日志面板） |
| 架构 | `core` 抓取器基类 / `fetchers` 抓取模块 / `extractors` 提取模块 / `gui` / `utils`，配置驱动 |

关键代码事实（[core/scraper.py](file:///workspace/core/scraper.py)）：
- `_setup_api_interception()` 通过 `page.on('response', handle_response)` 直接拦截 XHR 响应并 `response.json()` 解析。
- 滚动 (`_scroll_to_bottom`) 仅用于触发更多 API 请求，**不依赖 DOM 结构**。
- 失败时 `_check_api_data_or_har()` 走 HAR 文件解析回退。

也就是说，本项目绕过了 UI，本质上是"披着浏览器外衣的 API 客户端"。

## 二、RPA 适合做什么、不适合做什么

### RPA（UiPath / Automation Anywhere / Power Automate / 影刀 / 阿里 RPA 等）擅长
- 重复性 UI 操作：表单填写、点击流转、跨系统搬运。
- 桌面应用 + Web 混合流程（Excel、ERP、邮件附件）。
- 没有 API、只能模拟人操作的"黑盒"系统。
- 需要人工在环（登录、验证码）的流程编排。

### RPA 不擅长
- 大批量数据抓取（慢、贵、易碎）。
- 需要逆向 API、解析 JSON、精细数据加工的场景。
- 需要长期维护、版本化、单元测试的工程化项目。
- 纯 Web 且已有现代浏览器自动化方案的场景。

## 三、本项目用 RPA 的适配性打分

| 评估项 | 现状 | RPA 是否更优 | 说明 |
| --- | --- | --- | --- |
| 数据抓取性能 | API 拦截，单页可拿全量 | ❌ 更差 | RPA 走 UI 点击翻页，4600+ 条会慢一个数量级 |
| 反爬规避 | 直接命中 API，绕过虚拟滚动 | ❌ 更差 | RPA 依赖 DOM，虚拟滚动/懒加载更难处理 |
| 登录态注入 | Firefox Cookie 自动读取 | ⚠️ 持平 | RPA 也能读浏览器，但无优势 |
| 维护成本 | Python 代码 + 单元测试 | ❌ 更高 | RPA 流程图难 diff、难 review、难测试 |
| 部署复杂度 | `pip install` + `playwright install` | ❌ 更高 | RPA 需安装 Studio/Agent + 授权 |
| 跨平台 | Win/Mac/Linux 均可 | ❌ 受限 | 多数 RPA 仅 Windows |
| GUI 界面 | 已有 PySide6 完整界面 | ❌ 无需替换 | RPA 不提供同等 GUI |
| 备份/增量/迁移 | 已实现 | ❌ 需重做 | RPA 没有现成等价能力 |
| 价格 | 开源免费 | ❌ 更贵 | 商业 RPA 按机器人/并发收费 |

**综合结论：本项目用 RPA 不是"更好"，而是"降级"。**

## 四、什么情况下 RPA 才有价值

仅在以下边缘场景，RPA 可作为**补充**而非替换：

1. **人工辅助登录场景**：某站点强制图形验证码/滑块，需要"人在环"补登录态。RPA 的"等待人工输入"编排更顺手。
2. **桌面+Web 混合**：例如要把抓到的数据自动填入某个本地 Excel/ERP 系统，且该系统无 API。RPA 擅长桌面自动化。
3. **运营非技术人员自助**：希望运营同学通过可视化流程图自行调整抓取步骤，不写代码。
4. **跨浏览器 profile 切换**：需要复用某个已登录的浏览器会话配置，RPA 的浏览器配置管理略方便。

但以上任一项，在当前项目里**均未出现强需求**。

## 五、推荐路径

- **主线保持 Playwright + Python**：这是本项目已验证的最佳路径，无需迁移。
- **若要"降本"，方向是直接调 API**：进一步把 `page.on('response')` 拦截升级为"直接 `httpx` 请求 `content_v2_user` API"，去掉浏览器开销，性能可再提升数倍。
- **若要"易用"，方向是 GUI/调度**：现有 PySide6 GUI 已够用；可加定时任务（cron/ APScheduler）实现无人值守。
- **RPA 仅作为可选插件**：仅在出现"必须人工过验证码"或"必须操作桌面软件"时再引入，且只封装该子流程，不替换主线。

## 六、待二次确认 / 需补充的信息

> 以下问题将进入提问流程，由决策者确认后再定稿计划文档。

1. **引入 RPA 的真实动机**：是为了"降本/提速/易维护"，还是为了"非技术人员可维护"，或是合规/采购要求？动机不同，结论可能不同。
2. **目标 RPA 产品**：是否有指定厂商（影刀/阿里/UiPath/Power Automate）？影响可行性与成本测算。
3. **是否有桌面端混合需求**：抓取结果是否要写入桌面软件（Excel/WPS/ERP）？若有，RPA 价值上升。
4. **是否允许"去掉浏览器直接调 API"**：这是比 RPA 更优的提速方向，需要确认是否接受。
5. **运行环境**：目标部署在 Windows 个人机 / 服务器 / Linux 容器？RPA 多数仅 Windows。
6. **是否需要人工在环登录**：是否存在验证码/滑块必须人工处理的场景？
7. **预算与授权**：是否接受商业 RPA 授权费用？
