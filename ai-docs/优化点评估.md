## 一、调研结论速览

GitHub 上同栈（Playwright + Python）的米游社/原神抓取项目里，本项目**功能完整度领先**（32 功能 + GUI + 三游戏 + 增量 + 备份），但**工程化与性能有明显短板**：抓取主路径每次仍启动浏览器、单线程 urllib、Cookie 仅 Windows、日志非实时、无 Docker/CI、数据存 .txt。这些正是优化空间所在。

---

## 二、痛点定位（基于代码审查）

### P1. 抓取主路径仍启动浏览器（最大浪费）
[fetchers/news/base.py](file:///workspace/fetchers/news/base.py) 的 `_process_page()` 每次都 `page.goto` + `wait_for_load_state("networkidle")` + `time.sleep`，即便最终走的是 `_fetch_all_via_api_direct()`（urllib 直接请求 API）。**API 直连成功时，浏览器纯属白启动**，每次浪费数秒到十几秒。

### P2. API 直连用 urllib 单线程
`_fetch_all_via_api_direct()` 用 `urllib.request` 逐页同步循环，无连接复用、无并发、无指数退避。三游戏 6900+ 条逐页串行，慢。自定义 `retry` 装饰器不如 `tenacity` 成熟。

### P3. Cookie 加载仅 Windows
[utils/cookie_loader.py](file:///workspace/utils/cookie_loader.py) `find_firefox_profile()` 依赖 `APPDATA` 环境变量，macOS/Linux 直接返回 None。项目 README 声称支持跨平台，实际登录态注入只工作于 Windows。

### P4. GUI 日志非实时流
[gui/workers.py](file:///workspace/gui/workers.py) 的 `ScraperWorker.run()` 用 `redirect_stdout` 把全部输出收进 buffer，**任务结束后一次性 emit**。抓取几千条时，用户界面长时间无输出，体验差且无法判断是否卡死。

### P5. 数据存储为 .txt + 正则解析
`_get_existing_urls()` 用 `re.findall(r'\((https?://[^\)]+)\)')` 从文本文件抽 URL 做增量去重，脆弱、易错、查询慢。无结构化存储（JSON/SQLite）。

### P6. 浏览器兜底路径未做资源屏蔽
兜底的 `_scroll_for_data()` 不 abort 图片/字体/CSS，流量与时间浪费。Playwright 官方推荐 `page.route("**/*.{png,jpg,woff,css}", abort)` 提速。

### P7. 抓取代码大量 print 而非 logger
`utils/logger.py` 已存在，但 `fetchers/`、`core/` 仍直接 `print`，无法分级、无法落盘、无法被 GUI 实时接管。

### P8. 无并发抓取三游戏
三游戏独立串行抓取，无 `asyncio.gather` / 线程池并行。

### P9. 无 Docker / CI / 定时任务
无 Dockerfile、无 GitHub Actions、无 cron 集成，部署与无人值守缺位（参考 MihoyoBBSTools 的多架构 Docker + GH Actions cron）。

### P10. 无数据建模与分发
无 Pydantic 模型（字段无类型安全）；无 RSS/JSON Feed 输出（参考 hoyolab-rss-feeds、hoyoverse-api 的多语言聚合）。

## 四、重点优化详解

### O1 + O2：抓取主路径去浏览器化 + httpx 化（最高优先级）
- **现状**：`_process_page()` 永远先启浏览器，即便 API 直连成功。
- **方案**：新增 `core/api_client.py`，三游戏 API 用 `httpx` 直接请求；**仅当 API 直连失败时才回退启浏览器**（保留现有 Playwright 拦截路径作为兜底）。
- **收益**：单次抓取从「启浏览器(数秒) + 逐页 urllib」变为「httpx 连接池并发」，预计三游戏全量抓取总耗时下降 5–10 倍。
- **风险**：失去浏览器自动注入 Cookie 的便利，需自行管理登录态（米游社新闻 API 目前无需登录态，微博/用户主页仍需 Cookie，保留浏览器路径覆盖这些场景）。

### O6：结构化存储 + post_id 去重
- **现状**：`.txt` + 正则抽 URL 做去重，脆弱。
- **方案**：新增 `core/storage.py`，默认 SQLite（`news.db`，按游戏分表，主键 `iInfoId`），可选 JSON。增量去重改为 `SELECT 1 FROM news WHERE game=? AND iInfoId=?`。
- **收益**：去重 O(1)、查询快、可统计、可迁移。参考 zzzspider 的"已处理 URL 持久化集合"与 mihoyo-ugc 的状态机。

### O4：Cookie 跨平台
- **现状**：仅 Windows。
- **方案**：`find_firefox_profile()` 增加 macOS（`~/Library/Application Support/Firefox/Profiles`）与 Linux（`~/.mozilla/firefox`）路径探测；可选支持 Chromium 系（`Cookies` SQLite + AES 解密需 `pycryptodome`）。
- **收益**：兑现 README 的跨平台承诺。

### O5：GUI 日志实时流
- **现状**：任务结束后一次性 emit。
- **方案**：`ScraperWorker` 改为逐行/逐条 emit（用 `queue` 或直接在 `redirect_stdout` 的自定义流里 emit），配合 `log_message` 信号实时刷新。
- **收益**：抓取几千条时界面持续滚动输出，用户可判断进度与是否卡死。

## 五、不做的项（明确排除）

- **不引入 RPA**（见上轮评估结论）。
- **不重写 PySide6 GUI**（现有界面已够用，仅改 workers 日志流）。
- **不替换增量/备份机制**（沿用现有配置，存储层在其下做适配）。
- **不实现 DS 签名**（O17，除非未来 API 加风控）。

## 六、待二次确认 / 需补充的信息

> 进入提问流程，由决策者确认取舍后填入计划文档。

1. **优化范围**：是做"性能优先包"（O1–O5）还是"全量工程化包"（O1–O18）？
2. **数据存储**：SQLite vs JSON vs 保留 .txt？影响 O6 落地形态。
3. **并发抓取**：是否接受 asyncio 改造（O3 会改动较多代码）？还是仅做同步 httpx 连接池（O2）即可？

5. **数据分发**：是否需要 RSS/JSON Feed 输出（O14）给第三方订阅？
6. **依赖升级**：是否接受引入 `httpx`、`tenacity`、`pydantic`、`openpyxl` 等新依赖？
